# NEAR near-real-time ingestion: provider options and choice

Requirement: final_master_prompt section 9 (optional near-real-time layer, forward-only, daily BigQuery stays the historical reconciliation authority, compare cost / consistency / finality / fields / rate limits before choosing, never present unfinalized events as finalized).

Probed 2026-11-12 from the development machine (one residential IP, no API keys, no accounts). Every number marked "measured" comes from those probes; everything else is quoted from the cited documentation.

## Chain facts that drive the sizing

- Mainnet block time is about 0.56 s (nearblocks `avg_block_time` 0.5607; head advanced 3,507 blocks in 2,000 s), so about 1.75 blocks/s and 10 shards per block.
- About 6 transactions per block (891,297 transactions on 2026-11-11 in `near_daily_tx`).
- Finality: `finality=final` blocks cannot reorg; `optimistic` and `near-final` can. The feed only reads `final`.

## Choice: dRPC public JSON-RPC, final blocks only, tx-only default

Terms: free, keyless, no signup, no billing. Shared public endpoint with no SLA; throttled to roughly 20 calls/s and 3-call batches. Override with `NEARESIS_RT_RPC_URL` if the owner later approves a keyed endpoint.

How the feed uses it (`services/ingestion/src/realtime/rpc.ts`):

- `block {finality: final}` gives the final head and, when the cursor is at the tip, the block itself. A height above the final head is never requested.
- `block {block_id: h}` for backlog heights; `UNKNOWN_BLOCK` below the head is a skipped height (retried 3 times first, then confirmed by the next block's `prev_height` chain).
- `chunk {chunk_id}` only for chunks included at this height (`height_included == h`, so a repeated header of a missed chunk is never counted twice) and only when `tx_root` is not the empty root. That is about 4 calls per block (7 calls/s) instead of 11 (19 calls/s, which is the provider ceiling and fell 77 s behind in 3 minutes in the first trial).
- Per block: `tx_count`, distinct `signers`, per-receiver transaction counts (exact); `gas_burnt` and `tokens_burnt` from chunk headers.
- Verified on 3 consecutive mainnet blocks against neardata outcome sums: the chunk-header `gas_used` / `balance_burnt` reported in block h+1 equal the outcome sums of block h exactly. So per-block gas/tokens are the previous block's execution (one-block shift, exact in total).
- Receipts: NULL (never 0) in the default mode. Counting them needs every chunk body (`--with-receipts`, 11 calls/block, exceeds the free ceiling at 1.75 blocks/s). neardata would provide receipts and executed outcomes in one call per block, which is why a FastNEAR subscription key is the recommended upgrade if the owner wants them.

Shared rate-limit coordinator: every call goes through `RedisTokenBucket` under the key `ingestion:rate:near-rpc:<host>` (50 ms spacing = 20/s ceiling; 429/503 penalize the bucket via `Retry-After`, default 5 s). Any historical backfill that later reads the same provider must acquire from the same key; the BigQuery/Explorer backfill uses different providers and is unaffected.

## Data model (`nearesis_live`, migration `011_realtime.sql`)

- `rt_blocks` (ReplacingMergeTree by `version`, key `height`): one row per final block with state, hashes, `prev_height`, block time, `observed_at`, `ingested_at`, counts, burns and (3-day TTL) signer and receiver arrays. One insert per block, so a block is all-or-nothing.
- `rt_minutes`, `rt_minute_receivers` (top 100 per minute): recomputed idempotently from stored blocks. State `provisional` while the minute is open or contains a non-final block, `final` once a later minute has started and every block is final; `complete` only when the feed was running for the whole minute.
- `rt_watermark`: height, hash, block time, head height, observed/ingested time, lag, first block, skipped heights, state `live | catching_up | stalled`.
- `rt_anomalies`: gaps, parent-hash mismatches, final-hash conflicts.
- `rt_reconciliation`: per UTC day versus `near_daily_tx.tx_count`.
- `source_watermarks` gets one `near-realtime` row per closed minute so the existing monitor feeder and `/sources` freshness see it.

## Finality, restart, reconciliation

- Only `final` blocks are written. `decideWrite` is the state machine: final is never overwritten by provisional or by a different final hash (anomaly, row kept); provisional is promoted by the same hash or replaced by a different one.
- Resume point = maximum stored height, so a restart cannot skip or repeat a range. Every block must chain to the stored tip through `prev_height` / `prev_hash`; a gap or parent mismatch stops the process (supervisor restarts it) and writes an anomaly instead of continuing.
- Reconciliation (`realtime/cli.ts reconcile`): only fully covered UTC days (a stored block before the day start and one after its end, unbroken parent chain) are compared; `MATCH`, `WITHIN_TOLERANCE` (0.01%), `DIFF`, `PARTIAL_COVERAGE`, or `PENDING_BQ`. BigQuery remains authoritative and nothing is overwritten.

## Exposure

- `GET /v1/realtime/freshness`: last observation time, last ingestion time, watermark, finality (`final`), historical coverage, collector lag, collector state (heartbeat older than 120 s is reported `stopped`), recent reconciliation, partial-day warnings, data-vintage limitations.
- `GET /v1/realtime/transactions-last-hour`: finalized total from complete final minutes only; provisional kept apart; missing minutes stated, never zero-filled.
- Draft metric proposal: `docs/metrics/proposals/realtime-transactions-last-hour.draft.json` (blocked on a rolling-hour grain; not submitted).
- Operation: `scripts/ops/supervise.sh start realtime` (opt-in, not part of `all`).
